## D-011: Phase 4 research — Package manager & runtime (npm, Node >=24)
- Ref: TS_PORT_RESEARCH.md §T01 (full options, rationale, tradeoffs, migration implications, and validation strategy per recommendation live there); research fragment produced by workflow wf_09df6180-960
- Options: per-recommendation option sets are enumerated in TS_PORT_RESEARCH.md §T01 field 5 ("TypeScript/Node options considered") with current-version evidence fetched 2026-07-07
- Decision: all of the following (cite as D-011(k)):
  1. [Reuse existing repo decision] Package manager (uv replacement; tie-break npm vs pnpm vs Bun) → npm (bundled with Node 24, npm >=11.16), npm ci in CI, no Corepack
  2. [Reuse existing repo decision] Runtime target and Node version floor → Node.js (not Bun) with engines.node ">=24"; CI matrix 24.x (Active LTS floor) + 26.x (Current)
  3. [Replace Python-specific tool with TypeScript equivalent] .python-version equivalent (pin-file convention) → .nvmrc containing "24", read in CI via setup-node node-version-file; kept consistent with engines via a meta-test
  4. [Fresh research required] packageManager field / Corepack policy → Omit packageManager and Corepack; declare devEngines (runtime node >=24, packageManager npm, onFail error)
  5. [Adapt existing repo decision] Lockfile policy (source gitignores uv.lock) → Commit package-lock.json (v3); npm ci + lockfile-drift check in CI; document the divergence with an inverse .gitignore comment
- Why:
  1. Uniform across all four May-June 2026 org TS repos; zero bootstrap; dependency-graph/dependency-review/setup-node-cache/Trusted-Publishing all work natively, while Bun's bun.lock is unsupported by the GitHub dependency graph and the POC's pnpm argument was monorepo-specific. [TS_EXISTING_REPO_REVIEW.md:59,122,183,296,605-611; https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/dependency-graph-supported-package-ecosystems]
  2. Matches the org's newest deliberate floor (contributors-please >=24, June 2026); verified Node 24 is Active LTS, Node 20 EOL Apr 2026, Node 22 maintenance on npm 10.9 (below the 11.5.1 Trusted Publishing floor); an npm-published CLI runs on consumers' Node so Bun-as-runtime adds a toolchain for no deliverable benefit. [https://endoflife.date/nodejs; https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/]
  3. .nvmrc is read by nvm, fnm, mise, and actions/setup-node (nvm ignores .node-version), preserving the source's single-source version-pin discipline with the widest manager compatibility; no org precedent existed so this was fresh research. [https://github.com/actions/setup-node; TS_PORT_INDEX.md:300-309]
  4. Corepack is removed from Node 25+ by TSC vote so the packageManager field no longer self-enforces, while npm 11's devEngines is checked on install/ci/run without Corepack; matches org repos' omission of packageManager. [https://github.com/nodejs/nodejs.org/issues/7555; https://socket.dev/blog/node-js-tsc-votes-to-stop-distributing-corepack]
  5. Every org repo commits its lockfile and difftree documents the reproducibility rationale; Node CI (npm ci, setup-node cache, dependency graph) is designed around a committed lockfile, so the source's documented-toggle intent is preserved with the ecosystem-appropriate value. [TS_EXISTING_REPO_REVIEW.md:481,519; /Users/stevemorin/c/py-launch-blueprint/.gitignore:9]

## D-012: Phase 4 research — Build & npm packaging (tsdown, ESM-only, Trusted Publishing)
- Ref: TS_PORT_RESEARCH.md §T02 (full options, rationale, tradeoffs, migration implications, and validation strategy per recommendation live there); research fragment produced by workflow wf_09df6180-960
- Options: per-recommendation option sets are enumerated in TS_PORT_RESEARCH.md §T02 field 5 ("TypeScript/Node options considered") with current-version evidence fetched 2026-07-07
- Decision: all of the following (cite as D-012(k)):
  1. [Adapt existing repo decision] Build tool for the publishable CLI+library (tie-break #3: tsup vs plain tsc vs ncc committed-dist) → tsdown (pinned 0.22.x) with two entries (src/cli.ts + src/lib.ts), dts, sourcemaps, shebang; tsc --noEmit stays as the separate typecheck gate
  2. [Reuse existing repo decision] Dual CJS/ESM vs ESM-only output → ESM-only ("type": "module"), no dual CJS build
  3. [Replace Python-specific tool with TypeScript equivalent] package.json packaging surface: exports map, bin entry, files whitelist (hatchling wheel/sdist analog) → Hand-authored root-only exports map ('.' with types+default, plus ./package.json), bin -> ./dist/cli.js, files: ["dist"]; do NOT use tsdown's exports auto-generation
  4. [Replace Python-specific tool with TypeScript equivalent] Dynamic git-tag versioning (hatch-vcs/setuptools-scm equivalent) → release-please-managed package.json version + runtime --version read from packaged package.json; never hardcode version in source
  5. [Reuse existing repo decision] npm publishing, provenance and attestations → npm Trusted Publishing (OIDC, id-token: write, protected 'npm' environment) with automatic provenance attestations; no NPM_TOKEN; keep tag-vs-version guard and document the token fallback for self-hosted runners
  6. [Omit with rationale] ncc committed-dist pattern for the main package → Omit from the npm CLI+library template (relevant only to a GitHub-Action packaging flavor, another topic's scope)
  7. [Adapt existing repo decision] Packaging validation tooling → publint + @arethetypeswrong/cli in the aggregate check script, npm pack --dry-run file-list assertion, and a packed-tarball smoke test (run bin, import lib from ESM and CJS require)
- Why:
  1. Preserves agent2linear's bundle-with-dts intent on tsup's officially designated successor: tsup is unmaintained (last publish 2025-11), tsdown is active (0.22.3, 2026-06-16) atop rolldown 1.0-stable (May 2026), and ncc/plain-tsc were already criticized in-org. [https://github.com/egoist/tsup; https://voidzero.dev/posts/announcing-rolldown-1-0]
  2. Every recent org TS repo is ESM-only (Synthesis default #3) and Node >=20.19/22.12 require(esm) removes the last consumer-side reason to ship CJS. [TS_EXISTING_REPO_REVIEW.md:567-571; https://nodejs.org/api/modules.html]
  3. package.json fields are the npm analog of wheel/sdist content lists; root-export-only follows contributors-please's semver contract, and a template should teach an explicit exports map validated by publint rather than a build-time rewrite. [TS_EXISTING_REPO_REVIEW.md:151,298; https://tsdown.dev/options/package-exports]
  4. Org-canonical release-please flow (explicitly maintained as py-launch-blueprint's mirror) supersedes tag-derived versions; the tag-vs-package.json guard preserves the source repo's integrity check. [TS_EXISTING_REPO_REVIEW.md:560-566,100,146; TS_PORT_INDEX.md:225-231]
  5. contributors-please already implements the exact pattern and npm docs confirm provenance is automatic under trusted publishing (npm >=11.5.1, Node >=22.14 runner). [https://docs.npmjs.com/trusted-publishers; TS_EXISTING_REPO_REVIEW.md:134-136,146]
  6. The org's own review twice rejects committed dist/ as a general template default — it exists solely for the GitHub Actions run-a-checked-in-bundle constraint. [TS_EXISTING_REPO_REVIEW.md:159-160,650-651]
  7. Extends contributors-please's pack-dry-run + dist-smoke check chain with the current maintained validators (publint 0.3.21, attw 0.18.4, verified 2026-07-07). [TS_EXISTING_REPO_REVIEW.md:132; https://registry.npmjs.org/publint]

## D-013: Phase 4 research — tsconfig & module format (NodeNext, strict union)
- Ref: TS_PORT_RESEARCH.md §T03 (full options, rationale, tradeoffs, migration implications, and validation strategy per recommendation live there); research fragment produced by workflow wf_09df6180-960
- Options: per-recommendation option sets are enumerated in TS_PORT_RESEARCH.md §T03 field 5 ("TypeScript/Node options considered") with current-version evidence fetched 2026-07-07
- Decision: all of the following (cite as D-013(k)):
  1. [Adapt existing repo decision] module / moduleResolution format → module: NodeNext (implies moduleResolution NodeNext + esModuleInterop), pure ESM with type:module and explicit .js import extensions
  2. [Adapt existing repo decision] Full strictness flag set (mypy strict + pyright strict parity) → strict + noUncheckedIndexedAccess + noImplicitOverride + noFallthroughCasesInSwitch + noImplicitReturns + allowUnreachableCode:false + allowUnusedLabels:false + exactOptionalPropertyTypes + verbatimModuleSyntax + isolatedModules; noUnusedLocals/Parameters delegated to the T04 linter (org ^_ convention)
  3. [Adapt existing repo decision] target / lib → ES2022 target+lib now; T01-gated bump (lib ES2024 if Node>=22, target ES2024 if Node>=24 per @tsconfig/node24)
  4. [Adapt existing repo decision] Source layout and emit ownership → src/ rootDir → dist/ outDir; root tsconfig.json is noEmit and typechecks src + tests; tsconfig.build.json (src-only, declaration+maps) exists only if T02 selects tsc-emit, else the T02 bundler owns emit
  5. [Fresh research required] TypeScript version pin → typescript ^6.0.3 (current stable), config kept free of all 6.0-deprecated options so it is TS 7.0 (Go-native, currently 7.0.1-rc) ready
  6. [Replace Python-specific tool with TypeScript equivalent] Dual-checker (mypy + pyright) equivalence → Single tsc via one tsconfig.json — CI (tsc --noEmit) and the editor language service read the same file, so the dual-checker redundancy disappears by design; pyright diagnostics beyond tsc's reach (unused symbols, unnecessary conditions) move to the T04 linter
- Why:
  1. Newest org repos (contributors-please, contributors-please-action) already use NodeNext, official handbook recommends it for Node-run CLIs/libraries, and it stays valid regardless of T02's build-tool choice (bundler-resolution without a bundler is the claim-npm anti-pattern the review bars). [https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html; TS_EXISTING_REPO_REVIEW.md:128,189,345]
  2. Synthesis mandates consolidating the org union (claim-npm trio + POC pair); the additions close the gap to mypy warn_no_return/warn_unreachable and pyright strict per the port index's own mapping. [TS_EXISTING_REPO_REVIEW.md:567-571; TS_PORT_INDEX.md:379]
  3. ES2022 is the unanimous org baseline; community node24 base (es2024) and TS 6.0's es2025 default justify a bump only once T01 fixes the runtime floor. [https://raw.githubusercontent.com/tsconfig/bases/main/bases/node24.json; TS_EXISTING_REPO_REVIEW.md:128,567-571]
  4. Reuses contributors-please's src/dist + contributors-please-action's noEmit shape while fixing claim-npm's under-checking of tests (source mypy checks tests/); T02 coupling stated, not decided. [TS_EXISTING_REPO_REVIEW.md:128,185-189,302; TS_PORT_INDEX.md:304-307]
  5. Org repos pin 5.3–5.9 only because they predate 6.0; 6.0 is the designated transition release and the recommended config uses nothing 7.0 removes. [https://github.com/microsoft/typescript/releases; https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html]
  6. The mypy/pyright split exists only because Python's CI checker and editor service are different programs; in TS they are the same engine reading the same config. [TS_PORT_INDEX.md:372-380; /Users/stevemorin/c/py-launch-blueprint/pyrightconfig.json]

## D-014: Phase 4 research — Lint & format (Oxlint + Oxfmt; drop taplo/yamlfmt)
- Ref: TS_PORT_RESEARCH.md §T04 (full options, rationale, tradeoffs, migration implications, and validation strategy per recommendation live there); research fragment produced by workflow wf_09df6180-960
- Options: per-recommendation option sets are enumerated in TS_PORT_RESEARCH.md §T04 field 5 ("TypeScript/Node options considered") with current-version evidence fetched 2026-07-07
- Decision: all of the following (cite as D-014(k)):
  1. [Fresh research required] Primary linter + formatter (ruff lint+format replacement; tie-break #2: Biome vs oxc vs ESLint+Prettier) → Oxlint (1.73.0, stable 1.x) as linter + Oxfmt (0.58.0 beta, exact-pinned) as formatter; Biome 2.5.2 + yamlfmt documented as the stability-first fallback
  2. [Adapt existing repo decision] Formatter style options (line width, quotes, semicolons, trailing commas) → printWidth 100, singleQuote true, semi true, trailingComma es5, endOfLine lf in .oxfmtrc
  3. [Replace Python-specific tool with TypeScript equivalent] Import sorting (ruff I / eslint-plugin-simple-import-sort intent) → Enable Oxfmt's built-in sortImports option (perfectionist-like algorithm, off by default)
  4. [Adapt existing repo decision] Per-context lint relaxations (ruff per-file-ignores for tests/* and __init__.py) → .oxlintrc.json overrides array with files globs for tests/** and **/*.test.ts, each relaxation commented; error severity elsewhere (no POC warn-laxity)
  5. [Adapt existing repo decision] Security-rule coverage (ruff S / flake8-bandit intent) → Layered: oxlint built-in security-adjacent rules (no-eval etc.) + CodeQL workflow carried by the CI topic + eslint-plugin-security deferred until Oxlint JS plugins leave alpha
  6. [Omit with rationale] TOML formatter (taplo; coupled to cog.toml keep decision) → Omit taplo and .taplo.toml; if the release-tooling topic keeps cog.toml (Synthesis default is release-please with JSON config), Oxfmt formats TOML anyway
  7. [Omit with rationale] YAML formatting (google/yamlfmt + .yamlfmt) → Omit yamlfmt; Oxfmt formats YAML (Prettier-compatible), validated at scaffold time with yamlfmt retained as documented fallback if Oxfmt YAML proves opt-in/unstable
- Why:
  1. The POC's sole rejection reason (Oxfmt alpha, no formatter) is obsolete — Oxfmt beta passes 100% of Prettier's JS/TS conformance tests and formats YAML/TOML/Markdown, uniquely preserving the source's one-fast-tool intent, while Biome 2.5 still cannot format YAML/TOML/Markdown. [https://oxc.rs/blog/2026-02-24-oxfmt-beta; https://biomejs.dev/blog/roadmap-2026/]
  2. agent2linear's Prettier config and the POC's Biome config independently agree on these values, so they are reused rather than re-derived; the source's 88-col is a Python norm, not portable intent. [TS_EXISTING_REPO_REVIEW.md:67,372; https://oxc.rs/docs/guide/usage/formatter/config-file-reference]
  3. Keeps import order as a formatting concern (matching the source's just format = ruff format + isort) with no extra plugin, carrying agent2linear's import-sort convention. [https://oxc.rs/docs/guide/usage/formatter/config-file-reference; py-launch-blueprint/Justfile:110-118]
  4. Oxlint's overrides (files globs + per-glob rules/plugins) is a direct structural equivalent of ruff per-file-ignores; the review explicitly marks the POC's warn-level laxity as not-to-reuse. [https://oxc.rs/docs/guide/usage/linter/config; py-launch-blueprint/pyproject.toml:119-124]
  5. Neither Oxlint (no security plugin among its 16 built-ins) nor Biome offers a node-security/bandit equivalent, so the intent is approximated via built-ins plus CodeQL, with the gap honestly documented. [https://oxc.rs/docs/guide/usage/linter/plugins; https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha]
  6. taplo's npm CLI is stale (0.7.0, last modified 2024-02-01) and the source needed a cargo install; TOML presence depends on the T-release cog.toml decision, and Oxfmt covers TOML either way. [npm view @taplo/cli (0.7.0, 2024-02-01, checked 2026-07-07); https://oxc.rs/blog/2026-02-24-oxfmt-beta]
  7. Consolidating YAML into the main formatter removes the go/make-install bootstrap while preserving the intent that every config format is machine-formatted. [https://oxc.rs/docs/guide/usage/formatter.html; TS_PORT_INDEX.md:336-345]
