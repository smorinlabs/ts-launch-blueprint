# Versioning and Release Management

This project uses automatic version management powered by
**release-please**. `package.json`'s `version` field is the single
source of truth, and it is bumped exclusively by release-please's
generated Release PRs — never hand-edited.

## Key Features

- **Automatic Versioning**: release-please scans Conventional Commits
  on every push to `main` and maintains a standing "Release PR" that
  bumps `package.json`, `.release-please-manifest.json`, and
  regenerates `CHANGELOG.md`.
- **Single Source of Truth**: `src/version.ts` imports `package.json`
  directly (`import packageJson from '../package.json' with { type:
"json" }`) and re-exports its `version` as `VERSION`; the bundler
  inlines it at build time. There is no separate generated version
  file to keep in sync.
- **CI/CD Integration**: the `publish.yml` workflow's `verify` job
  asserts the release tag, `package.json`, and the manifest all agree
  before anything is published.
- **Semantic Versioning**: `bump-minor-pre-major: true` and
  `bump-patch-for-minor-pre-major: true` keep bumps semver-correct
  before and after 1.0.0.
- **Changelog Generation**: `CHANGELOG.md` is generated by
  release-please from the same commits, grouped by the
  `changelog-sections` mapping in `release-please-config.json` (feat →
  Features, fix → Bug Fixes, perf → Performance Improvements, docs →
  Documentation, test → Tests, refactor → Code Refactoring, chore →
  hidden).

## Creating Releases

Releases are cut by merging release-please's Release PR — there is no
manual tagging step in normal operation:

1. Push Conventional Commits to `main` (enforced by commitlint; see
   [Configuration Files](./configuration-files.md)).
2. release-please opens or updates a Release PR titled
   `chore(release): publish vX.Y.Z`, bumping `package.json`, the
   manifest, and the changelog.
3. Merge the Release PR. release-please tags the merge commit
   `vX.Y.Z`.
4. The `v*` tag push triggers `publish.yml`: a `verify` job (quality
   gates, build, packed-file-list assertion) must pass before the
   `publish` job — gated behind a protected `npm` GitHub Environment
   requiring human approval — runs `npm publish` using npm Trusted
   Publishing (OIDC; no long-lived npm token in the repo).

```bash
# Check version surface consistency (package.json, manifest, latest v* tag)
just release-status

# Local packaging validation (build, publint, attw, npm pack --dry-run,
# pack + install into a scratch dir, bin + ESM smoke test)
just pack-check
```

See [Release Runbook](../maintainers-release.md) for the one-time
GitHub Environment / npm Trusted Publisher setup and the full routine
release flow.

## Daily Development with Version Management

```bash
# Install dependencies
npm install

# Check the version the built CLI reports
just build
just version
# -> ts-projects 0.1.0

# Check the version.ts / package.json source of truth directly
node -e "console.log(require('./package.json').version)"
```

`tests/version.test.ts` pins three invariants: `VERSION` equals
`package.json`'s version, `VERSION` has a semver shape, and the
library entry point (`src/lib.ts`) re-exports the identical value.

## CI/CD Automation

Two workflows implement the release pipeline end to end:

### `release-please.yml`

- **Trigger**: every push to `main` (plus manual `workflow_dispatch`).
- **Action**: runs `googleapis/release-please-action` against
  `release-please-config.json` / `.release-please-manifest.json`,
  creating or updating the standing Release PR.
- Uses the built-in `GITHUB_TOKEN` by default, which means merging the
  Release PR tags the release but does **not** auto-trigger
  `publish.yml` (a `GITHUB_TOKEN`-authored push cannot fire other
  workflows). The workflow file documents, in a commented block, how to
  upgrade to a GitHub App token so the tag push auto-triggers publish.

### `publish.yml`

- **Trigger**: push of a `v*` tag.
- **`verify` job** (unprivileged, no registry access): checks out full
  history, confirms the tag is an ancestor of `main`, confirms
  `tag == package.json version == manifest version`, runs `just all`,
  builds, and asserts the packed file list is exactly `dist/**` plus
  the `package.json`/`README.md`/`LICENSE`/`CHANGELOG.md` whitelist.
- **`publish` job** (needs `verify`): runs inside the protected `npm`
  GitHub Environment (human-approved), mints an OIDC token, and runs
  `npm publish` — npm Trusted Publishing exchanges the OIDC token for a
  short-lived credential, so no npm token secret is stored anywhere.

## Troubleshooting Versions

### Version Issues

- **`package.json` version looks stale**: check whether an open
  Release PR is waiting to be merged (`just release-status` reports
  drift between `package.json` and the latest `v*` tag).
- **Version mismatch in CI**: the `verify` job in `publish.yml` fails
  the release if the tag, `package.json`, and the manifest disagree —
  this should only happen from a manual/out-of-band tag push; let
  release-please manage tags instead.
- **`VERSION` doesn't match `package.json` in tests**: rerun `just
build` — `src/version.ts` reads `package.json` at build time via the
  bundler's JSON import, so a stale `dist/` can lag a version bump.

### Workflow Issues

- **Release PR not appearing**: confirm commits on `main` use
  Conventional Commit types that release-please recognizes (`feat`,
  `fix`, etc. — see `release-please-config.json`'s
  `changelog-sections`); `chore` commits are tracked but hidden from
  the changelog and don't trigger a version bump on their own.
- **Merging the Release PR didn't publish**: with the default
  `GITHUB_TOKEN` auth, the tag push from the bot does not trigger
  `publish.yml`. Either push/re-run the tag manually, or configure the
  GitHub App token upgrade documented in `release-please.yml`.
- **`publish` job never runs**: it waits for approval in the protected
  `npm` environment — configure required reviewers under this
  repository's Settings > Environments (see
  [Release Runbook](../maintainers-release.md)).
- **`npm publish` fails with an auth error**: the npm Trusted Publisher
  must be configured on npmjs.com for this package (repository owner/
  name, workflow file path `.github/workflows/publish.yml`, environment
  name `npm`) before the OIDC exchange can succeed.
